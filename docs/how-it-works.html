How the platform works

This is not “ask an LLM to look at a database”. The system builds an organisational semantic understanding layer over every connected system, then lets an AI investigate that whole ecosystem like an analyst would — decomposing metrics, following relationships into other domains, weighing evidence, and citing the exact query behind every number.

The core idea

Most “chat with your data” tools point a language model at one table and hope. That fails on the questions that matter, because the answer to “why did revenue drop?” is almost never inside the revenue table. It is in HR (a team left), in inventory (a product went out of stock), in operations (deliveries slipped), in support (complaints spiked) — spread across systems that use different names for the same customer.

So the platform inverts the problem. It spends its effort on understanding first:

Catalog everything

Every source is discovered, profiled column by column, classified for PII, and described in business terms.

Unify the meaning

Governed metrics, a business glossary, and canonical entities that resolve customer_id = customer_code = client_id.

Map the connections

A reviewed relationship graph that says which tables join to which, and how — within and across systems.

Then reason

The AI navigates that map, runs targeted read-only SQL, and must back every claim with a query reference.

The rule that shapes everything: no evidence, no claim. Numbers come from executed queries, never from the model's memory. Correlation is always labelled as correlation. When data is missing, the answer says so instead of guessing.

Running the app

Double-click start.bat in the project root. On the first run it sets everything up; afterwards it just starts.

  1. Checks prerequisites

    Python 3.11+ and Node 20+ must be on your PATH. It tells you what is missing rather than failing cryptically.

  2. Installs dependencies (first run only)

    Creates .venv, installs the backend requirements, then runs npm install for the frontend. This takes a few minutes once.

  3. Builds the demo (first run only)

    Generates the synthetic enterprise dataset and seeds the catalog: 7 sources, 19 governed metrics, glossary, entities, relationships and insights.

  4. Picks a free port

    Tries 8000, then 8010, 8020… and writes the winner into frontend/.env.local so the UI always talks to the right backend.

  5. Starts both servers and waits

    Opens two windows — backend and frontend — polls until both answer, then opens your browser at the app.

Architecture

Seven layers, each usable on its own. Data flows up from the sources; a question flows down from the top and comes back as an evidence-backed answer.

1 · Connectors

Every source type implements one small interface, and registers itself. The core never imports a database driver, so adding a source does not touch the reasoning engine. 

class DataConnector:
    def test_connection(self): ...
    def list_databases(self): ...
    def list_schemas(self): ...
    def list_tables(self): ...
    def get_schema(self, table): ...
    def sample_data(self, table, n): ...
    def execute_query(self, query, limit, timeout): ...
    def get_row_count(self, table): ...
    def get_statistics(self, table): ...
CategorySupportedHow it is queried
DatabasesPostgreSQL, MySQL / MariaDB, SQL Server, Oracle, SQLite, DuckDBQueried live, in place. Aggregation is pushed down; only results come back.
FilesCSV, TSV, Excel (each sheet becomes a table), JSON, JSONL, Parquet, XMLRead by DuckDB directly — streamed, so a large file never lands in memory.
NoSQLRedis, MongoDBNormalised into tables, then queryable as SQL.
APIsREST (bearer / basic / key header, paginated), GraphQLFetched, flattened, schema auto-detected, materialised.
BI modelsPower BI semantic models, Tableau Server / CloudRows materialised and the platform's own semantic model imported — see below.

Redis needs care, because it is not relational. Keys are scanned by pattern and normalised by prefix: hashes and JSON documents under order:* become an order table with real columns, while lists, sets and sorted sets land in a generic redis_keys table with their key, type, TTL and value. Mongo documents are flattened the same way — nested {"v":{"x":1}} becomes a column v_x — without altering the source.

Why everything ends up as SQL. Sources that cannot be queried relationally are materialised into a private DuckDB file per source. One query path means one place to enforce read-only rules, permissions and row limits — and the AI never needs to learn six query languages.

2 · Metadata catalog

Connecting a source kicks off a pipeline that ends with the source fully described:

Profiling computes, per column: row and null counts, null percentage, distinct count and cardinality, duplicates, min / max / mean / median / standard deviation, percentiles, IQR outliers, frequency distribution, date range, and sample values. From those numbers it infers a semantic type — is this an identifier, a measure, a dimension, a date, a flag? — which is what later lets the system decide that region is worth decomposing by and order_id is not.

PII detection runs on both column names and value patterns (email, phone, Aadhaar, PAN, credit card with a Luhn check, bank account, IP). Each column gets a sensitivity of public sensitive pii restricted, which drives masking everywhere downstream.

Descriptions are suggested, never silently applied. Heuristics write a first draft; an AI model can propose better business descriptions, semantic types and units. Both appear as suggestions in the UI that a steward accepts or edits — and every accepted edit creates a version you can look back at.

3 · Semantic layer

This is where raw columns become business language. Four things live here.

Governed metrics

A metric is a formula the organisation agrees on, so the AI never invents its own arithmetic:

name        revenue
formula     SUM(revenue)
filters     —                          # posted_revenue uses: invoice_status = 'POSTED'
date column order_date
unit        INR          format  currency      direction  up
dimensions  region, product_id, channel, discount_pct, customer_id, employee_id

The dimensions list is what the investigation engine decomposes by. Point-in-time metrics — headcount, for instance, where you count people active during a period rather than events inside it — use placeholders: 

sales_headcount   COUNT(*)
  WHERE department = 'Sales'
    AND hire_date < '{period_end}'
    AND (exit_date IS NULL OR exit_date >= '{period_start}')

Business glossary

Definitions, owners, synonyms and rules. Synonyms matter more than they look: they are how the planner recognises that “turnover”, “top line” and “sales revenue” all mean the revenue metric. Rules capture the fine print — revenue is recognised when invoice status is POSTED; cancelled invoices are excluded; currency is INR.

Canonical entities — cross-system resolution

The same customer is called four different things in four systems. An entity maps them to one identity:

Search and versioning

Everything in the catalog — tables, columns, metrics, glossary terms, relationships — is indexed for search. It is a hybrid: a BM25 lexical score always, plus cosine similarity over embeddings when an embedding model is configured. This is what turns the vague phrase “employee attrition” into the concrete tables and metrics worth looking at. And every definition change is versioned, with a before/after diff and an author.

Search never replaces querying. It is used only to find where a concept lives. The number itself always comes from SQL executed against the authoritative source.

Importing a BI platform's semantic model

Power BI and Tableau already hold governed definitions — measures with formulas, declared relationships, curated field descriptions. Re-deriving that would be both wasteful and less accurate than what the business already agreed on, so it is imported directly.

From the BI modelBecomes
Table & field descriptionsTable descriptions and column business definitions
Measures (DAX / Tableau formulas)Governed metrics
Declared relationshipsRelationships, pre-approved — the BI model is authoritative
Format stringsMetric unit and format (currency / percent)

Formulas are translated by a real parser, not pattern matching:

SUM('Sales'[Revenue])                                        ->  SUM("Revenue")
COUNTROWS('Orders')                                          ->  COUNT(*)
DIVIDE(SUM('S'[Profit]), SUM('S'[Revenue]))                  ->  (SUM("Profit")) / NULLIF((SUM("Revenue")), 0)
CALCULATE(SUM('I'[Amount]), 'I'[Status] = "POSTED")          ->  SUM("Amount")   WHERE "Status" = 'POSTED'
[Revenue] - [Cost]                                           ->  inlined from the other measures
Try it without a tenant. python scripts/bi_demo_stubs.py starts local stand-ins for both platforms that speak the real wire protocols, and prints the exact settings to paste into Add data source. The same stubs back the integration tests.
What cannot be translated is refused, not guessed. Time intelligence (TOTALYTD, SAMEPERIODLASTYEAR), context transitions (ALL, ALLEXCEPT, FILTER), iterators (SUMX), formulas spanning two tables, Tableau window functions — each of these is imported as a definition only metric. It keeps its native formula, stays searchable and quotable, and the engine refuses to produce a number for it. The AI is told the same and must explain the definition rather than estimate. A silently mistranslated measure would produce a confident wrong answer — exactly the failure this platform exists to prevent.

4 · Relationship graph

Relationship discovery compares every identifier-like column against every other, combining five signals: declared foreign keys, name similarity with business aliases (cust→customer, sku→product, emp→employee), type compatibility, cardinality (is one side unique?), and — the decisive one — actual value overlap measured on sampled distinct values. 

Suggested relationship
  sales.customer_id  →  crm.accounts.customer_code        confidence 94%
  Reason: name similarity 100%, matching types, 99.2% of sampled identifiers overlap
Nothing high-impact is created silently. Discovery only suggests. A human approves or rejects each one, and the AI traverses approved relationships only. You can see exactly which joins the reasoning is allowed to use.

Approved relationships plus entity mappings form a graph whose nodes are tables. Breadth-first traversal from a starting table finds everything reachable within N hops, and that is precisely how a question about revenue reaches the HR table — not because someone hard-coded it, but because the path exists: 

sales ──(employee_id → employee_id)──> hr
sales ──(entity:Product)────────────> inventory
sales ──(entity:Customer)───────────> support
sales ──(order_id → order_id)───────> finance_invoices

5 · Query engine

Every query — whether typed by a person, generated from a metric, or written by the model — passes through the same gate.

  1. Validate

    Single statement only. SELECT / WITH only. Writes, DDL and dangerous functions (read_csv, pg_sleep, xp_cmdshell, file and network access) are blocked — with string literals stripped first, so a keyword inside 'DROP TABLE x' is harmless.

  2. Authorise

    Referenced tables are resolved against the catalog and checked against the user's role. A denied table or a restricted column stops the query before it runs.

  3. Apply row-level security

    Any row filter for the role is injected as a filtered sub-select, so FROM hr silently becomes FROM (SELECT * FROM hr WHERE department = 'Sales').

  4. Generate native SQL

    Each dialect gets its own syntax — DATE_TRUNC on Postgres, DATEFROMPARTS on SQL Server, DATE_FORMAT on MySQL, FETCH FIRST on Oracle, TOP n instead of LIMIT.

  5. Execute with limits

    Row cap and statement timeout enforced per dialect. Aggregation happens in the database; only summarised rows travel.

  6. Mask and log

    PII columns are masked for non-admins, then the query is written to the log with a reference like Q-3F9A1C22 — the handle every citation in every answer points back to.

6 · Investigation engine

This is the heart of the system, and it contains no AI at all. It is deterministic: the same question over the same data produces the same evidence every time. An LLM is used afterwards to write, not to compute.

  1. Validate the headline

    Compute the metric for both periods and the twelve-month trend.

  2. Decompose by every dimension

    Region, product, channel, customer, salesperson… each segment gets its own change and its contribution to the total movement.

  3. Find the real drivers

    A big segment moving with the market is not a driver. The engine keeps only segments whose change is disproportionate — far from the overall change — and ranks them by contribution × excess.

  4. Walk the graph

    Up to three hops out, collecting every governed metric on every reachable table — finance, HR, inventory, support, operations, marketing.

  5. Re-cut related metrics by the drivers

    Each related metric is recomputed for the driver segments and their intersection. This is what turns “deliveries got worse” into “deliveries for Product C in the West went from 5% late to 71% late”.

  6. Check timing

    A metric that moved sharply in the previous month is flagged as a possible lagged cause — seven people leaving in July shows up in August's revenue, not July's.

  7. Correlate and caveat

    Monthly series are correlated, always labelled as correlation. Open data-quality issues and the freshness of every source touched are attached to the result.

Independent analyses run concurrently, each on its own database session, so an investigation spanning five systems and roughly sixty queries finishes in about three seconds. Every figure it produces carries the query reference that produced it.

7 · AI reasoning layer

Planning first, not prompting first

A question is parsed before any model sees it: intent, metric, period, comparison, dimensions, domains.

"Why did revenue decline in August?"
  intent      diagnostic
  metric      revenue            (matched via catalog + glossary synonyms)
  period      August 2026        comparison  July 2026
  domains     finance, sales

If no period is given but the question implies a direction — “why did revenue drop?” — the planner scans recent months and anchors on the most recent real decline, then says so in the plan. Follow-ups inherit context: “was it because of attrition?” keeps revenue as the subject and treats attrition as the hypothesis to test, rather than switching topic.

Provider-agnostic

Two wire protocols cover every vendor: the OpenAI-compatible chat API (OpenAI, Azure, Gemini, Ollama, OpenRouter, vLLM, LM Studio, anything compatible) and the Anthropic Messages API. Different models can serve different jobs — a cheap one for metadata descriptions, a strong one for reasoning, a separate one for embeddings. Tokens, latency and cost are tracked per request.

Tools, not table dumps

The model never receives raw tables. It receives the plan and a compact summary of the investigation, and can call permission-checked tools for anything else: search_metadata, find_relevant_datasets, get_schema, get_column_profile, get_relationships, get_entity_mapping, calculate_metric, compare_periods, detect_anomalies, get_data_quality, execute_sql, execute_python_analysis, generate_chart. Repeated calls are de-duplicated and the loop is capped, so a weaker model cannot spin.

Guardrails on the output

Citations are verified

Every Q- reference in the narrative is checked against queries that actually ran. Invented ones are struck through and marked unverified, a warning is attached, and confidence drops.

Claims are classified

Observed fact, calculated metric, correlation, potential explanation — each with strong / medium / weak strength.

Confidence is computed

From evidence strength, open quality issues, stale sources and analysis warnings — not from the model's self-assessment.

Sandboxed analysis

Python for statistics runs in a subprocess with an import whitelist, no file access, no environment, a timeout and a result cap.

The answer

The narrative is organised as Executive Summary → Key Findings → Cross-Domain Evidence → Likely Contributors (split into evidence-supported, potential, and insufficient evidence) → Recommended Investigation → Confidence. Alongside it sit five tabs: every evidence item with its kind and strength, generated charts, all SQL with results, the sources used with their freshness and open quality issues, and the plan and reasoning path including every tool call the model made.

Clicking any Q-3F9A1C22 in the text opens the exact query, the source it ran against, and the rows it returned.

Follow-ups keep the thread

Ask “was it because of employee attrition?” and the subject stays revenue; attrition becomes the hypothesis under test, with the July timing made explicit. Ask “which region?” and it decomposes the same metric over the same period. Ask “compare with last year” and only the comparison period changes.

Data quality

Quality checks run after every profile and feed directly into how much the AI trusts its own answer.

RuleCatches
Missing valuesHigh null rates — with optional event columns like exit_date downgraded, because a null there means “still employed”, not “broken data”.
Duplicate keys / rowsPrimary keys that are not unique; fully duplicated records.
Invalid valuesNegative amounts, prices or quantities.
OutliersIQR-based, on columns where it is meaningful.
Inconsistent categories"West" vs "west " vs "WEST".
Volume changeRow count moving ±30% between ingestions — the classic silent truncation.
Schema driftColumns or types that changed since the last sync.
FreshnessHow old the newest record is, per source.

Open issues on any table used in an analysis are surfaced inside that analysis and lower its confidence rating.

Proactive insights

The system does not wait to be asked. The insight engine sweeps every governed metric's monthly series for month-over-month shocks and z-score anomalies, then runs a shallow investigation on each one so the finding arrives with its context already attached: 

Revenue declined 14.7% in August 2026                              [warning]

  1. By region: 'West' moved −38.0% vs −14.7% overall  (66% of the change)   strong
  2. By product: 'Product C' moved −19.9% vs −14.7% overall (68%)            strong
  3. Delivery delay rate rose 111.7%; West × Product C 5% → 71% late         strong
  4. Sales headcount fell 33.3% in the West (24 → 16)                        strong

  5 related metrics checked across Finance, HR, Inventory, Sales, Support.
  [ Investigate with AI ]

The dashboard ranks them by severity and magnitude, and “Investigate” hands the question to the assistant pre-filled.

Security

Authentication

JWT sessions, bcrypt password hashing.

Roles

admin / analyst / viewer, enforced on every endpoint.

Object permissions

Allow or deny per dataset, table or column. One allow rule flips that role to default-deny.

Row-level security

SQL predicates injected into every query on a table for that role.

PII masking

Applied to results for non-admins based on the detected sensitivity.

Read-only by default

Writes and DDL are rejected before reaching any source.

Encrypted secrets

Connection credentials and API keys encrypted at rest, masked in responses.

Full audit trail

Logins, edits, permission changes, questions and executed queries — all searchable.

The assistant inherits your permissions. It is not a privileged service account. If you cannot see salaries, neither can the AI answering your question — it will say the data is restricted rather than working around you.

Extending it

To add…Do this
A data source typeSubclass DataConnector (live SQL) or MaterializedConnector (produces frames), set type_key / config_fields, decorate with @register. The UI form builds itself from the field list.
A metricMetrics → Define metric. Available to the AI immediately, versioned automatically.
A business ruleA glossary rule, or a metric filter such as invoice_status = 'POSTED'.
An AI toolAdd a spec to TOOL_SPECS and a matching t_<name> method on ToolBox.
A quality ruleExtend run_quality_checks.
A SQL dialectAdd an entry to dialects.py — month truncation, date ranges, row limiting, prompt hints.

The reasoning engine never needs to change for any of these. That is the point of the layering.

SymptomCause and fix
Assistant answers without a narrativeNo AI provider configured, or its test fails. Check Administration → AI Providers. The deterministic analysis shown is still fully valid.
A local model is slow or ramblesUse a tool-capable model and raise num_ctx in the provider's extra settings. Small models handle the investigation summary poorly.
